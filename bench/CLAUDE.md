# `bench/` — the benchmarks, and the performance conventions they hold up

Read this before optimizing or restructuring a hot path in `src/`: the conventions are here because each one is a measurement, and the file that proves it is in this folder.

**Hot paths are hand-written; cold paths stay idiomatic.** A path is _hot_ when it runs per WebSocket frame, per packet, per batch element, per stream chunk, per broadcast recipient, or per SSE line. Everything else — startup, router definition, introspection, reconnect, subscription resume, per-connection handshake, CLI codegen — is _cold_, and there `.map`/`.filter`/spread/`Object.entries` are the preferred spelling because they read better. This is a rule about **where**, not a ban on **what**: `.map` in `router.js` at definition time is correct code, and the same call per packet is not.

On a hot path, prefer a manual indexed loop, preallocate with `new Array(len)` and truncate with `result.length = index` rather than growing, and use `for (const key in obj)` over `Object.entries(obj)` when the object is one this package built. Never write `push(...array)` — it is `Function.prototype.apply` in disguise and throws `RangeError` once the array exceeds the engine's argument limit, which turns a large cluster fan-in into a hard failure rather than a slow one (the fan-in of `fetchClients` in `src/rpc/cluster.js`). The established examples are `applyMask` in `src/websocket/frame.js` (word-wise XOR through a `Uint32Array` view), the once-sweep of `emit` in `src/utils.js` (preallocate + index cursor + truncate, in place of `.filter`), and `SegmentQueue` in `src/websocket/segments.js`.

**A hot-path hand-optimization must cite its benchmark in a comment.** If the win is not measured, the code is only harder to read — so the comment names the file that proves it, as the comment over `applyMask` in `src/websocket/frame.js` cites `bench/unmask.js` and the one over `Emitter` in `src/utils.js` cites `bench/emitter.js`. New measurements go in a new top-level file under `bench/`; `bench/run-all.js` discovers it automatically. Capture before and after by hand — the harness in `bench/support/harness.js` prints ops/sec but stores no baseline, and nothing in CI runs `pnpm bench`.

**Do not convert a `switch` or an `if`/`else if` chain into a table of handler functions.** The intuition that a table is the O(1) answer to a linear branch chain is half right, and the half that is wrong is the half that matters here. `bench/dispatch.js` measures all three shapes on this codebase's own discriminants: with the branch cost isolated, a 9-branch chain really is linear (165 M ops/s at the first branch, 69 M at the last) and a `switch` is flatter — but once a real handler call is in the loop, the call dominates and `switch` and the chain come out level (55.1 vs 55.0 M ops/s), while a table loses ~25% in every shape tested (42.4 M ops/s). V8 compiles a `switch` over string literals into direct comparisons and keeps the call target inlinable; a table yields a function _value_, which it cannot inline through, and `Object.freeze` and `Map` do not close the gap. So the branch chains of `handlePacket` in `src/rpc/dispatcher.js`, `#dispatch` in `src/client/core.js` and `#line` in `src/sse/client.js`, and the `switch (t)` in `src/rpc/cluster.js`, stay as they are. If a chain ever does become the bottleneck, order its branches by frequency first — that is free and keeps the guards next to the conditions they justify.

**The dispatch tables that do exist are for late registration, not for speed.** `WrpcClient.transport` (`static transport` in `src/client/core.js`) and `ServerTransport.transport` in `src/transport.js` are plain object literals looked up as `TABLE[key]` and guarded with `typeof x !== 'function'`, and are deliberately **not** frozen, because a subpath entrypoint registers into them at require time (`WrpcClient.transport.sse` in `src/sse/client.js`, `WrpcClient.transport.webrtc` in `src/webrtc/transport.js`). Use that idiom when a third party must be able to add a case; freeze the table when the set is closed (`DISABLED` in `src/logging.js`). A table keyed on anything **peer-controlled** additionally needs `__proto__: null` or `Object.hasOwn` — a plain literal answers `TABLE['toString']` with a real function, which passes the `typeof` guard and silently swallows a packet that should have produced an honest error. `assignKey` in `src/rpc/router.js` and the two `Object.hasOwn` hops of `member` in `src/query/index.js` already defend against this.

**A defensive copy is not an allocation to eliminate.** `Client#rooms` (`get rooms` in `src/rpc/client.js`) exists so a caller can iterate while leaving; the copies the chainable `Broadcast` in `src/rpc/rooms.js` makes in `to`/`except` are what make `b.to('a')` non-mutating; the listener snapshot on `Emitter.emit`'s multi-listener path guards against `off()` from inside a listener; and `Array.from(set)` in `src/scaling/redis.js` is required because that loop calls handlers synchronously. Where such a copy is genuinely unnecessary — `publish` in `src/scaling/memory.js`, whose loop only schedules microtasks — say so in a comment, so the asymmetry reads as a decision rather than an oversight.

**Some allocations are load-bearing for security, not correctness.** `Object.fromEntries(new URLSearchParams(...))` — `parseParams` in `src/rpc/dispatcher.js` — looks like an easy win and is not: `fromEntries` uses `CreateDataProperty`, so a `?__proto__=x` query string lands as an own property, while a hand-rolled `obj[key] = value` loop reintroduces prototype pollution on peer-controlled input. The cost there is the `URLSearchParams` parse anyway, not `fromEntries`.

**Browser-reachable files are on a byte budget, and manual loops cost source bytes** — which files, and how a budget is raised, is in `src/CLAUDE.md`. Optimize there only with a measurement that justifies the bytes.

**Two lint rules shape hot-path code.** `no-labels` is an error with `allowLoop: false`, so a manual loop may not use a labelled `break`/`continue` — restructure into a helper with an early `return` instead. `array-callback-return` is an error, so a `.map`/`.filter` callback must return on every path.
