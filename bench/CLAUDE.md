# `bench/` — the benchmarks, and the performance conventions they hold up

Read this before optimizing or restructuring a hot path in `src/`: the conventions are here because each one is a measurement, and the file that proves it is in this folder.

**`src/` iterates with loops, hot or cold.** Since 2.3 `src/` has no array iteration method anywhere — `js-conventions` of alexiskills says why, and lint enforces it — so the old split, where `.map`/`.filter`/`Object.entries` were the preferred spelling on a cold path, is gone. What a path's heat still decides is the hand-optimization. A path is _hot_ when it runs per WebSocket frame, per packet, per batch element, per stream chunk, per broadcast recipient, or per SSE line; everything else — startup, router definition, introspection, reconnect, subscription resume, per-connection handshake, CLI codegen — is _cold_, and there a loop is written to be read.

On a hot path, `new Array(len)` filled by index and truncated with `result.length = index` stays where a benchmark here measured it, citing it in a comment with `// oxlint-disable-next-line unicorn/no-new-array` (the once-sweep of `emit` in `src/utils.js`, `bench/emitter.js`); elsewhere an array is built packed with `push`. `for...of` over an iterable and `for...in` over a plain object are fine in `src/` since alexiskills 1.1.2, and a hot path keeps the loop its benchmark picks, cited at the site: `for...in` where V8 walks a small object from its enum cache faster than `Object.keys` with an index loop (`eachHeader` in `src/adapters/common.js`, `metaUpperBound` in `src/rpc/dispatcher.js`), `Object.keys` for a thousand-key presence snapshot — both measured in `bench/object-walk.js`. A loop that replaced `every`, `some`, `map` or `filter` on an array the caller passes skips holes (`if (!(i in list)) continue;`), as the method did. Spreading into a call is guarded site by site (`CALL_SPREADS`); the fan-in of `fetchClients` in `src/rpc/cluster.js` is the failure it prevents. The established examples are `applyMask` in `src/websocket/frame.js` (word-wise XOR through a `Uint32Array` view), the once-sweep of `emit` in `src/utils.js`, and `SegmentQueue` in `src/websocket/segments.js`.

**A hot-path hand-optimization must cite its benchmark in a comment.** If the win is not measured, the code is only harder to read — so the comment names the file that proves it, as the comment over `applyMask` in `src/websocket/frame.js` cites `bench/unmask.js` and the one over `Emitter` in `src/utils.js` cites `bench/emitter.js`. New measurements go in a new top-level file under `bench/`; `bench/run-all.js` discovers it automatically. Capture before and after by hand — the harness in `bench/support/harness.js` prints ops/sec but stores no baseline, and nothing in CI runs `pnpm bench`.

**How a row is measured** (`node-performance-profiling`): the harness (`bench` in `bench/support/harness.js`) warms a case, cuts its time into five windows and prints their median with the spread (`±x%`), keeps what the case answers in a sink so V8 cannot drop the work, and awaits only what is a promise — awaiting a plain value cost a sync case a microtask per iteration. A bench that `src/` cites for a decision runs **one case per process**: `if (!isolate(__filename)) main();` (`isolate` and `selected` in `bench/support/isolate.js`) — the parent spawns the file once per case, so no case inherits the call-site feedback and the garbage of the ones before it. `bench/emitter.js`, `bench/object-walk.js`, `bench/dispatch.js` and `bench/unmask.js` do, the last two calling `selected()` from their own timers once per case. A hand-written timer warms an eighth of its run first (`bench/deflate-js.js`, `bench/attachments.js`, `bench/send-path.js`, `bench/message-compression.js`).

**Do not convert a `switch` or an `if`/`else if` chain into a table of handler functions.** The rule is `js-conventions`' own now (its `performance.md`), measured here: `bench/dispatch.js` runs all three shapes on this codebase's discriminants — with a real handler call in the loop, `switch` and the chain come out level (55.1 vs 55.0 M ops/s) and a table loses ~25% (42.4 M), because V8 inlines through a `switch` and not through a function value read from a table. So the branch chains of `handlePacket` in `src/rpc/dispatcher.js`, `#dispatch` in `src/client/core.js` and `#line` in `src/sse/client.js`, and the `switch (t)` in `src/rpc/cluster.js`, stay as they are. If a chain ever does become the bottleneck, order its branches by frequency first — that is free and keeps the guards next to the conditions they justify.

**The dispatch tables that do exist are for late registration, not for speed.** `WrpcClient.transport` (`static transport` in `src/client/core.js`) and `ServerTransport.transport` in `src/transport.js` are plain object literals looked up as `TABLE[key]` and guarded with `typeof x !== 'function'`, and are deliberately **not** frozen, because a subpath entrypoint registers into them at require time (`WrpcClient.transport.sse` in `src/sse/client.js`, `WrpcClient.transport.webrtc` in `src/webrtc/transport.js`). Use that idiom when a third party must be able to add a case; freeze the table when the set is closed (`DISABLED` in `src/logging.js`). A table keyed on anything peer-controlled is `{ __proto__: null }` or read through `Object.hasOwn`, as `js-conventions` says: `assignKey` in `src/rpc/router.js`, the two `Object.hasOwn` hops of `member` in `src/query/index.js`, `STATUS_CODES` in `src/status.js` and `DECODERS` in `src/broker/feed.js`.

**A defensive copy is not an allocation to eliminate.** `Client#rooms` (`get rooms` in `src/rpc/client.js`) exists so a caller can iterate while leaving; the copies the chainable `Broadcast` in `src/rpc/rooms.js` makes in `to`/`except` are what make `b.to('a')` non-mutating; the listener snapshot on `Emitter.emit`'s multi-listener path guards against `off()` from inside a listener; and `Array.from(set)` in `src/scaling/redis.js` is required because that loop calls handlers synchronously. Where such a copy is genuinely unnecessary — `publish` in `src/scaling/memory.js`, whose loop only schedules microtasks — say so in a comment, so the asymmetry reads as a decision rather than an oversight.

**Some allocations are load-bearing for security, not correctness.** `Object.fromEntries(new URLSearchParams(...))` — `parseParams` in `src/rpc/dispatcher.js` — looks like an easy win and is not: `fromEntries` uses `CreateDataProperty`, so a `?__proto__=x` query string lands as an own property, while a hand-rolled `obj[key] = value` loop reintroduces prototype pollution on peer-controlled input. The cost there is the `URLSearchParams` parse anyway, not `fromEntries`.

**Browser-reachable files are on a byte budget, and manual loops cost source bytes** — which files, and how a budget is raised, is in `src/CLAUDE.md`. Optimize there only with a measurement that justifies the bytes.

**Three lint rules shape a loop.** `no-labels` is an error with `allowLoop: false`, so a loop may not use a labelled `break`/`continue`, and `max-depth` is 4 — restructure into a helper with an early `return` or `continue` instead; `array-callback-return` still holds where `tests/` and `bench/` use `.map`/`.filter`.

## The comparisons over real stacks

```bash
node bench/http-comparison.js   # wrpc's HTTP paths vs fastify/express/tRPC/node:http under autocannon (fastify/benchmarks' settings; WRPC_BENCH_DURATION seconds per stack)
WRPC_WT=fails WRPC_RTC=node-datachannel node bench/transports.js   # wrpc over ws/WebTransport/WebRTC on real stacks (bench/support/real-stacks.js; needs node scripts/wt-cert.js certs) — rows skip without the variables; the same gate adds the wt/webrtc rows to bench/rpc-comparison.js
WRPC_WT=fails pnpm bench:browser transports   # the same from Chrome (bench/browser/transports.js); without WRPC_WT the WebTransport row is skipped
```
