# `src/encryption/` — application-level encryption

Cross-cutting rules — the protocol revision, no runtime dependencies, commands, the package layout — are in the root `CLAUDE.md`; the layering of `src/` and the hot-path conventions are in `src/CLAUDE.md`. A rule lives in ONE file: add to the file of the folder it is about.

`src/encryption/` — application-level encryption behind the `@alexify/wrpc/encryption` subpath (experimental; the third subpath with a `browser` condition), opt-in and NEVER a substitute for TLS — it is for where TLS ends before the data does (backplane, broker log, TLS-terminating proxy, a relay that should not read). Phases land one commit each (keyring envelopes for rooms/cluster/brokers, a sealed session store, canonical Noise on ws/wt, HPKE per request on HTTP/SSE, pairwise E2EE helpers).

Landed so far — the primitives: `contracts.js` (the structural seams `isCipher`/`isCipherKey`/`isDh`/`isKeyProvider` and the ONE failure `OpenError` — a wrong key, nonce, bit or length are indistinguishable on purpose; a `Cipher` is `{ id, keyLength, nonceLength, tagLength, key(raw) -> { seal(nonce, pt, aad), open(nonce, sealed, aad) } }`, the prepared key existing for the browser's one-time non-extractable `CryptoKey` import — on Node it measures as a wash), `aead.js` / `aead.browser.js` (the platform pair swapped via `package.json#browser`: `'aes-256-gcm'` + Node-only `'chacha20-poly1305'` SYNCHRONOUS over `node:crypto` — 2.4 µs against 14 µs through subtle on the same machine, `bench/encryption.js` — vs promise-answering `crypto.subtle` AES-GCM, where ChaCha is `null` under `optional`), `dh.js` / `dh.browser.js` (`x25519()`, id `'25519'` as Noise names it — the SECOND platform pair of the directory: `node:crypto` KeyObjects on Node because subtle's X25519 prints an `ExperimentalWarning` on early Node 22 (22.10 yes, 22.23 no; run the suite under `~/.nvm/versions/node/v22.10.0` to see it), `crypto.subtle` in a browser, where the public key of a seed is the function applied to the base point, so a private key is never exported; a low-order point is refused with one error whether the platform throws or answers zeros), `hkdf.js` / `hkdf.browser.js` (`createKdf()` — SHA-256/HMAC/HKDF with Extract and Expand APART, because Noise and HPKE need them apart and subtle's own `'HKDF'` only does both), `keyring.js` (`normalizeKeys`: one key → kid `'0'`, `{ current, ring }`, or a SYNCHRONOUS provider; a kid is `[A-Za-z0-9._-]{1,32}`, peer-controlled, held in a `Map`, and SELECTS the key — never trial decryption), `bytes.js` (Buffer-free plumbing, `counterNonce` = 4 zero bytes ‖ u64 BE as Noise gives AESGCM, `randomSource`/`requireSubtle` — there is NO `Math.random` fallback in this directory, a missing `crypto.getRandomValues`/`crypto.subtle` throws where the factory is called).

Everything but the AEAD, DH and HKDF pairs is ONE file for both platforms (Node ≥ 22 has the browser's WebCrypto), with `subtle` an injectable default parameter exactly like `src/webrtc/assertions.js`.

Node-only on top: `envelope.js` — sealed envelopes for the Node↔Node carriers (`normalizeEnvelopeEncryption` → `{ keys, cipher, seal, acceptPlaintext, replayWindow }`, `createEnvelopeSealer({ encryption, layer })`, `ReplayWindow`): frame `u8 version ‖ u8 suite ‖ salt16 ‖ u64 counter ‖ ct ‖ tag`, NEVER a random nonce — each process derives its own key with `hkdfSync(master, salt, 'wrpc <layer> v1\0kid\0cipher')` and counts under it, reseeding at 2^32 (GCM's random-nonce bound is hours away on a busy fan-out); AAD = `'wrpc-sealed v1\0layer\0kid\0channel'`; the receiver's per-(kid, suite ‖ salt) entry — derived key + sliding replay window — is remembered ONLY after a tag verified (a flood of made-up salts evicts nobody), LEAST RECENTLY USED out past `maxSenders` (1024 by default; LRU, not oldest-first, so a busy sender evicted by a newcomer does not come back with a fresh window that re-opens a frame just refused as a replay); both built-in suites are always openable so a cipher change is config, not rollout; an injected cipher is probed for synchrony like a codec in `normalizeSyncCompression`; the sealer answers `null` for its OWN salts (the last `MINE_KEPT`, 16), which spares a publisher decrypting + parsing every echo.

It is composed with compression by `src/rpc/envelope.js` (`createEnvelope`, built by the core and injected into `RoomsBackplane`/`Cluster` in place of `createEnvelopeCodec` — identical to it when `encryption` is off): ONE frame, `wrpc-sealed:<kid>:base64(sealed(u8 flags ‖ [idLen ‖ codec id] ‖ body))`, compress-then-seal with a single base64; `decode` answers the text, `null` (the callers' `*.encoded` warning) or `undefined` for a refusal it already logged itself (`*.unsealed`, `*.open` with a log-only `reason`) — and rooms/cluster name a still-sealed envelope `*.sealed` AFTER decode, because a compression-only codec passes through what is not its own.

BYTES cross the backplane through the same composer: `createEnvelope` is now ALWAYS an object (`withBytes(inner)` — identity for text when no option is on, so the no-option path costs one call and one `charCodeAt`), with `encodeBytes(envelope, channel)` = `wrpc-bin:` + base64 of `encodeAttachments(envelope)` (the encoder is generic over any object) or, sealing, the same bytes inside the sealed frame under flag bit 1; `decode` may therefore answer an OBJECT, which `rooms.js` already tolerated — its `*.sealed` check is guarded by `typeof text === 'string'`. `Broadcast.emit` passes `binary: true` instead of refusing; `RoomsBackplane.publish` feature-detects `encodeBytes` and still warns `backplane.bytes` for a registry wired by hand. An instance with NO codec must still answer `null` for a `wrpc-enc:` message (`isEncodedEnvelope`) — the loud `*.encoded` warning is a tested behaviour. The envelope seam takes the `channel` as a second argument for this (`cluster.js` binds it per subscription).

Cluster HMAC is untouched: sign → seal, open → verify. Rollout is three deploys (`seal: false, acceptPlaintext: true` → `acceptPlaintext: true` → neither) because pub/sub is at-most-once.

`store.js` — `sealedStore(store, { keys, cipher?, acceptPlaintext?, logger? })` over the structural `SessionStore`: row key = `HMAC-SHA256(hkdf(master, 'wrpc store-index v1\0kid'), token)` base64url (the raw bearer token used to BE the Redis key), value = `{ v: 1, kid, s }` (an object, because the Redis store rejects non-objects) sealed by the same envelope sealer under layer `'store'` with `echo: true` (a store reads back what it wrote — the own-salt shortcut is a backplane thing) and `replayWindow: false`, AAD = the row key; a miss under the current kid walks `keys.kids` and MIGRATES the row (so rotation is not a mass logout — and the index key rotates too), `acceptPlaintext` does the same for a row the unwrapped store wrote; a row that does not open is `null` + one warning, the token never logged.

SESSION encryption (client↔server, ws): `noise.js` (one file, both platforms — Noise rev 34 under CANONICAL names `Noise_{NN,NK,XX,NNpsk0}_25519_{AESGCM,ChaChaPoly}_SHA256`, verified against the cacophony vectors in `tests/encryption/vectors/noise.json` on BOTH primitive halves; every primitive call is awaited because subtle answers promises; `CipherState` takes its counter SYNCHRONOUSLY so calls made in order are sealed in order and a `Sequencer` only keeps results so; the ChaChaPoly nonce is little-endian, AESGCM big-endian; deterministic `REKEY` every 2^20 messages; `ephemeral` is a test-vector-only option), `session.js` (the shared framing: first handshake `00 05 ‖ ver ‖ nameLen ‖ name ‖ kidLen ‖ kid ‖ noise`, later `00 05 ‖ noise`, sealed `00 06 ‖ AEAD(u8 inner ‖ payload)`; prologue = `'wrpc.v1\0kind\0' ‖ hello header` — `PROLOGUE_LABEL` in `src/encryption/session.js`, the label of THIS framing and deliberately not the negotiated core revision, so the vectors do not move with it; the inner frame uses `Buffer.write` behind a `typeof Buffer` guard — 0.4 vs 1.0 µs on 1 KB, `bench/encryption.js`), `statics.js` (ONE secret per kid → `HKDF(secret,'wrpc noise static v1')` and `…'wrpc hpke static v1'` — never one key for two protocols; the pinned bundle is `kid:noisePub:hpkePub`), `client.js` (`createEncryption` → the INJECTED object `{ param: 'wrpc_e', secure(link) }`; never falls back to plaintext; verifies the server key BEFORE sending XX's third message, which carries the client's own static; inbound frames are taken through a promise chain until it drains, because the server is established the moment it wrote its last message and its sealed frames arrive while the client is still finishing), `server.js` (Node-only: `normalizeServerEncryption` — protocols held in a `Map` by NAME, a peer's name is looked up never parsed, refused never negotiated — and `SealedSocket`, an `EventEmitter` wrapper around the ENGINE socket that re-emits `('message', data, isBinary)`, so `attachSocket`, the dispatcher, compression, attachments and chunks are untouched and one wrapper serves node, uws and wt; it offers NO `sendPrepared`/`sendUnreliable`, so a broadcast to sealed clients is N seals; sends before the handshake are queued up to 256; `ready` never rejects — it resolves `null` after closing; one close reason `'encryption'`, 1002 crypto/parse vs 1008 policy).

Core wiring: `RpcServer` option `encryption`, `#sealSocket` (the mode is announced by `wrpc_e=1` in the connect URL because the SERVER may send first — `wantsEncryption(meta.url)`), the restore thunk awaits `sealed.ready` and sets `client.encryption`, `attach(…, { encrypted })` + `handleHttpCall` refuse under `required` (426), `encryptionKey()`.

Client wiring: `static encrypts = true` on a transport that carries it, `WrpcClient.#checkEncryption` over every fallback candidate up front, `worker` + `encryption` is a TypeError (the option belongs to `WrpcClientProxy`, which forwards it).

On WebTransport (`src/client/webtransport.js`) the same injected object runs over the control stream after the caps exchange with kind `'wt'` in the prologue, and the three ways around the channel are switched off under it: `StreamMux` is `null` (as under a codec — so no `streams` cap, chunks ride the control stream), no datagram writer/reader, `#compression` forced `null`; `#attach` returns the handshake promise so `open()` resolves only once sealed. The SERVER needed no wt change at all — `attachSession` → `attachSocket` wraps the `WtSocket`, and `SealedSocket` offering neither `streamControl` nor `sendUnreliable` is what turns the server's mux and datagrams off. `tests/websocket/protocolClient.js` now keeps the query string of its URL.

PER-REQUEST encryption (http): `hpke.js` (one file — RFC 9180 base + psk modes, `dhKem(dh, kdf)` = DHKEM(X25519, HKDF-SHA256) with `deriveKeyPair`, `isKem` the seam where ML-KEM is injected, `HpkeContext` seal/open by sequence-XOR nonce + `export`; verified against the RFC vectors in `tests/encryption/vectors/hpke.json` on both primitive halves; AEAD ids 2/3 only — AES-128 is not in `aead()`), `http.js` (shared + client: the format `ver ‖ aeadId ‖ kidLen ‖ kid ‖ enc ‖ ct`, plaintext `u32 headerLen ‖ JSON{m,u,h,t} ‖ body`, response `nonce32 ‖ AEAD(u32 ‖ JSON{s,h} ‖ body)` keyed RFC 9458 §4.4-style from `context.export`; `sealedFetch` wraps a `fetch` and answers a real `Response`, so `ClientHttpTransport` changed by one block; a non-sealed response is an ERROR whatever its status), `httpServer.js` (Node-only: `createHttpSealing` → `unwrap(call, corsHeaders)` answers the INNER call marked `encrypted` whose `respond` seals — outer status always 200, `Set-Cookie` kept OUTER because script cannot set HttpOnly — plus `createReplayCache`; freshness = `t` within `maxSkew` and `enc` accepted once; refusals go through the core-injected `refuse(call, headers, status, reason)`: bare status, reason in the log).

Core: one block in `handleHttpCall` after the origin check — discovery `GET <basePath>/encryption-key`, then `unwrap`, then the `required` gate (426) — so packet, batch and REST modes are untouched. The fastify adapter registers the `application/wrpc-sealed` buffer parser (else 415) and the `/encryption-key` route (one static segment the parametric route never matches); `tests/adapters/boots.js` forwards `encryption`.

SSE rides the same binding and needed NO change in `src/sse/server.js`: `unwrap` gives the inner call a `stream()` (only when the request's `accept` names `text/event-stream`; the key is `streamKey` in `src/encryption/http.js` — HKDF-Extract over `enc ‖ serverNonce` of `context.export('wrpc sse stream')`, then Expand — with a fresh server nonce drawn per stream, so a replay of the request onto another instance opens a stream under another key; derived in `unwrap` because the core opens the stream synchronously) whose writer seals every written chunk — events, the `ready` frame with the channel id, the heartbeat comment — as `data: <base64>` under a counter nonce, type `text/event-stream; wrpc-sealed=1; n=<serverNonce>` (Content-Type PARAMETERS because that is the one response header a cross-origin page can always read); sealed at the WRITER, so the replay ring stays plaintext in process memory and `resume()` is untouched, and every (re)attached stream has its own key and counts from zero — which replaced the plan's "nonce = event id" design and its channel-key persistence; the client half is `openSealedStream` in `http.js` (a `ReadableStream` that turns the outer events back into the real stream's bytes for an `SseParser` that never knew; an injected comment line is skipped, anything that does not open errors the stream). `unwrap` deletes the outer `accept-encoding` from the merged headers: a content coding inside a sealed answer would reach a client that reads the bytes as they are. `ClientSseTransport` wraps its injected `fetch` exactly like the http transport.

`hkdf.js` / `hkdf.browser.js` became the THIRD platform pair by measurement: a sealed request is 219 µs both ends with node:crypto HMACs vs 565 µs over subtle (a threadpool hop per HMAC), a Noise handshake 291 vs 745.

END-TO-END helpers (`e2ee.js`, shared): `createIdentity(seed?)` (the SEED is the secret to keep, and exists for PORTABILITY — the same identity from the same seed on another device; a browser that never needs that keeps a non-extractable `x25519().generateKeyPair()` pair in IndexedDB and hands it to `createOpener`/`senderKey` directly), `createSealer`/`createOpener` — one HPKE context PER MESSAGE (`enc ‖ ct`; two clients may never be online together, so nothing is kept in step), HPKE AUTH mode when a `senderKey`/`senderPublicKey` is given (an anonymous or differently-signed message does not open, and an opener expecting nobody does not open an authenticated one either — the modes differ in the key schedule), `info` = `'wrpc e2ee v1'` ‖ the application's purpose string. Deliberately NOT a messaging protocol (no recipient FS, no group key, no replay memory — the sender-key helper of the plan was CUT; MLS/Double Ratchet ride the same bytes) and, in a browser, no defence against the origin that ships the script. `hpke.js` has all four RFC 9180 modes for it (`mode = (auth ? 2 : 0) + (psk ? 1 : 0)`).

`browser.js` is the shared barrel, `index.js` spreads it and adds the Node-only halves as they land.

Two rules added after the phases above: `authorize` admits a connection only by answering `true` (as the client's `verifyServer` always did), and what a peer sends while this end's handshake is still running is bounded on both ends — `MAX_HELD` frames or `MAX_HELD_BYTES` in `src/encryption/session.js`, past which the server closes 1008 (reason `held`) and the client fails its `open()`.
